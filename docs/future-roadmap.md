# NBA Draft DB 将来ロードマップ

この文書では、MVP完了後に追加する機能と構成を整理する。MVPの範囲は [MVPロードマップ](mvp-roadmap.md) を参照する。

## 1. 将来構成

```text
データ収集・検証
        ↓
正規化された正本データ
        ├─ Cloudflare D1
        │       └─ Cloudflare Workers API
        │               └─ Webサイト / 検索 / 選手詳細
        │
        ├─ Looker Studio用の集計データ
        │
        └─ バックアップ・エクスポート
```

Cloudflare D1は、MVPで検証したスキーマと集計要件が固まった後に導入する。D1を新しい正本にする場合でも、SQLiteまたはSQLダンプでバックアップ・復元できる運用を維持する。

## 2. Phase 5: D1とAPI

- MVPのスキーマをD1へ移行する
- マイグレーションファイルを管理する
- Cloudflare WorkersからD1を読み取る
- 選手一覧APIを作る
- 選手詳細APIを作る
- ドラフト年・指名順位・ドラフト区分の検索APIを作る
- APIレスポンスに最終更新日時と出典情報を含める
- 読み取り専用APIとして公開するかを判断する

## 3. Phase 6: Webサイトの拡張

- ドラフト年別ページ
- 選手詳細ページ
- ドラフト順位別ランキング
- ドラフト外選手の一覧
- キャリア年数による絞り込み
- オールスター選出回数による絞り込み
- 選手間比較
- URLで検索条件を共有できる機能

Looker Studioは分析用、Webサイトは検索・閲覧用として役割を分ける。

## 4. Phase 7: データ更新の自動化

- データ取得スクリプトを整理する
- 取得データと正規化済みデータを分離する
- 定期実行の仕組みを導入する
- 更新対象のシーズンだけを差分取得する
- 取得失敗やデータ件数の急減を検知する
- 更新前後の件数と集計値を比較する
- 問題がある場合に公開データへ反映しない仕組みを作る

自動更新では、取得処理と公開処理を分離する。取得しただけでは公開せず、検証に成功したデータだけをD1やLooker Studio用出力へ反映する。

## 5. Phase 8: 統計項目の拡張

- プレーオフ成績
- All-NBA
- MVP
- Rookie of the Year
- Defensive Player of the Year
- Sixth Man of the Year
- All-Defensive Team
- 得点王などのシーズンリーダー
- チーム在籍期間
- トレード履歴
- 大学・海外経歴
- ドラフト前評価と実績の比較

賞や選出は `player_honors` の種類を増やす形で拡張し、集計ロジックを特定の賞に依存させない。

## 6. Phase 9: 品質管理と再現性

- 外部データの取得元をテーブル単位・行単位で管理する
- データ取得日時を保存する
- 過去データのスナップショットを保存する
- 選手IDの対応表を管理する
- 名前変更や表記揺れを検知する
- 主要な集計値をテストする
- 同じ入力から同じ出力が生成されることを確認する
- D1の定期バックアップを作る

特に、選手名だけでの結合は避ける。外部ソースごとのIDと、プロジェクト内の正規IDの対応を管理する。

## 7. Phase 10: 公開・運用の改善

- 独自ドメイン
- ページのメタデータとOGP
- データ更新履歴ページ
- 出典ページ
- エラー監視
- アクセス解析
- キャッシュ戦略
- APIのレート制限
- 必要に応じた認証付き管理機能

## 8. 将来の判断ポイント

### D1を導入するタイミング

- 選手検索をサイト上で実装したい
- JSONファイルの生成・配信だけでは運用しづらい
- データ更新頻度が上がった
- 複数の画面から同じデータを参照したい

### Google Sheetsを経由しないタイミング

- Looker Studio用データの自動出力が必要になった
- 行数や更新処理がGoogle Sheetsに向かなくなった
- BigQueryや別のLooker Studioコネクタを利用する価値が出た

### 無料構成を見直すタイミング

- CloudflareまたはGoogleの無料枠を継続的に超える
- 自動更新処理の実行時間が増える
- APIアクセスが増える
- バックアップ要件や可用性要件が高くなる

## 9. 将来の最終形

最終的には、以下を満たすデータ基盤を目指す。

- 一つの正規データモデルから複数の表示先へ出力できる
- 選手、ドラフト、シーズン、賞をIDで正確に結合できる
- データ更新を再現可能な処理として実行できる
- Looker Studioで分析できる
- Webサイトで個別検索・閲覧できる
- すべての主要データに出典と更新履歴がある
